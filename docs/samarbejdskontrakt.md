## 4. Arbejdsform

### Dokumentations-strategi

Hvor skal dokumentationen ”leve”?

**Vores aftale**

- Levende dokumenter på Teams
- Diagrammer i /docs på GitHub (
- 

### Branching-strategi

Hvad skal være på en branch? Hvordan navngives branches? Hvornår merges der til main?

**Vores aftale**

- Der arbejdes aldrig direkte i main-branch
- Alle ændringer foregår på feature branches
- Acceptance Criteria (AC) & Definition of done skal være opfyldt før merge til develop
- Branch: Feature Branch --> Dev-Branch --> Deployment/main

### Brug af commit, push og pull

Aftal hvordan i foretrækker at arbejde f.eks. hyppighed, indhold og struktur for commit-messages.

**Vores aftale**

- Pull først inden man begynder at kode
- Commit ofte og med korte, præcise beskeder
- Push hurtigt efter commit, så andre kan hente ændringer
- Merge konflikter løses i fællesskab, men den GitHub-ansvarlige har det endelige ansvar

### Pull requests og kodegennemgang

Skal alle pull requests godkendes af mindst én anden? Hvordan sikrer vi, at vi ikke overskriver hinandens
kode?

**Vores aftale**

- Pull requests skal reviewes og godkendes af én der ikke har skrevet koden (peer review)

## 5. Kvalitet og kodestandarder

### Code style og formatering

Relevante overvejelser: Hvilke Java-navngivningskonventioner skal anvendes? Skal vi bruge fælles
autoformat og deler vi evt. en IDE-konfiguration? Hvordan dokumenterer vi processen f.eks. vha. JavaDoc?

**Vores aftale**

- Vi er alle ansvarlige for at skrive kommentarer/JavaDoc løbende mens vi koder
- Ift. navngivning anvender vi camelCase (f.eks. metoder) og PascalCase (f.eks. klasser), snake-case til feature branches

## 8. Deadlines og milepæle

### Milepæle og rettidig aflevering

Vil vi lave faste milepæle? Hvordan sikrer vi, at vi rammer dem?

**Vores aftale**

- Delmål aftales løbende i gruppen via sprint planning og fremgår af vores Scrum Board

endelige afleveringsfrist

### Fælles forståelse og præsentation

Alle skal kunne forklare den fælles kode.
